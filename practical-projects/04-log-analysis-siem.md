# Project 04 — Log Analysis and a Basic SIEM Investigation Workflow

Alerts are cheap; investigations are not. In this project you generate a realistic but entirely synthetic log set, index it in a free SIEM, write searches that detect credential attacks and data access, and then work the result like an analyst: validate, scope, correlate, decide, and document. The goal is a repeatable workflow you can defend in an interview, not a dashboard screenshot.

| Field | Value |
| --- | --- |
| Difficulty | Intermediate–Advanced |
| Estimated time | 8–12 hours |
| Cost | $0 |
| Prerequisites | Projects 01–03; comfort with regular expressions and structured logs; a VM with 4 GB RAM free |
| Safety and scope | Synthetic logs only; Splunk Free has no authentication, so bind it to localhost; never index real customer or employer data |

`Last reviewed: 2026-10-31`

> **Safety and scope.** Every event in this project is generated by the script in the setup, using documentation IP ranges and fictional accounts. Do not replace the dataset with production logs. If you later analyze real logs from a system you own, remove personal data, credentials, and customer identifiers first, and get written permission if anyone else's data is involved. Splunk Free is single-user and unauthenticated: bind the web port to `127.0.0.1` and reach it through an SSH tunnel.

## Objective

- Generate a deterministic synthetic dataset with three log sources: Linux authentication, web access, and JSON application events.
- Index the data in Splunk Free and confirm each sourcetype is searchable.
- Write and save detections for SSH brute force, successful login after failures, privileged command execution, and anomalous data export.
- Correlate the same actor across all three sources and build a minute-level timeline.
- Produce a triage report with severity, confidence, false-positive analysis, containment recommendations, and detection gaps.

## Why this project matters

A SIEM is only as useful as the questions you ask it. Most beginners learn the interface and stop there, so their investigations become clicking until something looks scary. Professionals work from a hypothesis: what would this attack look like in each data source, what would a benign explanation look like, and what evidence would distinguish them? This project forces that discipline on a dataset small enough to reason about completely.

The synthetic approach has a second benefit: you know the ground truth. You can check whether your detection missed the successful login, whether your correlation picked up the wrong IP, and whether your timeline is complete. That self-check is impossible with a real incident you joined halfway through.

## Setup

### Build the SIEM VM

1. Create `lab-siem` with 2 vCPUs, 4 GB RAM, and a 30 GB disk on the host-only network at `192.168.56.50`. Install Ubuntu Server 24.04 and Docker Engine using the official instructions.
2. Add your user to the Docker group, then log out and back in:

```bash
sudo usermod -aG docker "$USER"
```

3. Create the log directory and start Splunk bound to localhost only. The password below is a lab placeholder; replace it with your own and never reuse it.

```bash
mkdir -p ~/siem/logs
export SPLUNK_PASSWORD='CHANGEME-lab-only'
docker run -d --name splunk \
  -p 127.0.0.1:8000:8000 \
  -e SPLUNK_START_ARGS=--accept-license \
  -e SPLUNK_PASSWORD="$SPLUNK_PASSWORD" \
  -e TZ=UTC \
  -v "$HOME/siem/logs:/logs" \
  splunk/splunk:latest
docker logs -f splunk
```

Wait for the log line indicating Splunk is ready, then open an SSH tunnel from your workstation and browse to `http://127.0.0.1:8000`:

```bash
ssh -L 8000:127.0.0.1:8000 labadmin@192.168.56.50
```

### Generate the synthetic dataset

Save this as `~/siem/make_logs.py` and run it. It writes three files and prints a summary. All addresses are from RFC 5737 documentation ranges and all accounts are fictional.

```python
#!/usr/bin/env python3
"""Synthetic log generator for Project 04. Safe, deterministic, documentation IPs only."""
import json
import random
from datetime import datetime, timedelta, timezone
from pathlib import Path

random.seed(42)
OUT = Path.home() / "siem" / "logs"
OUT.mkdir(parents=True, exist_ok=True)
BASE = datetime(2026, 10, 31, 13, 0, 0, tzinfo=timezone.utc)
ATTACKER = "203.0.113.45"
NORMAL = ["192.0.2.10", "192.0.2.11", "198.51.100.7"]

def stamp(dt):
    return dt.strftime("%b %d %H:%M:%S")

auth, access, events = [], [], []
for i in range(8):
    t = BASE + timedelta(minutes=i * 9)
    auth.append(f"{stamp(t)} lab-siem sshd[{2000+i}]: Accepted publickey for labadmin from 192.0.2.10 port {40000+i} ssh2: ED25519 SHA256:lab")

for i in range(60):
    t = BASE + timedelta(seconds=180 + i * 25)
    user = random.choice(["admin", "root", "svc-backup", "oracle", "test"])
    auth.append(f"{stamp(t)} lab-siem sshd[{3000+i}]: Failed password for invalid user {user} from {ATTACKER} port {50000+i} ssh2")

t_success = BASE + timedelta(minutes=27, seconds=40)
auth.append(f"{stamp(t_success)} lab-siem sshd[4000]: Accepted password for svc-backup from {ATTACKER} port 51422 ssh2")
t_sudo = t_success + timedelta(minutes=2)
auth.append(f"{stamp(t_sudo)} lab-siem sudo: svc-backup : TTY=pts/1 ; PWD=/home/svc-backup ; USER=root ; COMMAND=/bin/tar -czf /tmp/backup.tgz /var/backups")

for i in range(80):
    t = BASE + timedelta(seconds=i * 20)
    ip = random.choice(NORMAL)
    access.append(f'{ip} - - [{t.strftime("%d/%b/%Y:%H:%M:%S +0000")}] "GET / HTTP/1.1" 200 {random.randint(400, 9000)} "-" "Mozilla/5.0"')

for i in range(25):
    t = t_success - timedelta(minutes=5) + timedelta(seconds=i * 3)
    access.append(f'{ATTACKER} - - [{t.strftime("%d/%b/%Y:%H:%M:%S +0000")}] "GET /admin HTTP/1.1" 401 512 "-" "python-requests/2.31"')

t_export = t_sudo + timedelta(minutes=3)
access.append(f'{ATTACKER} - - [{t_export.strftime("%d/%b/%Y:%H:%M:%S +0000")}] "GET /api/v1/export HTTP/1.1" 200 5242880 "-" "python-requests/2.31"')

events.append({"ts": t_success.isoformat(), "event": "auth.login", "user": "svc-backup", "src_ip": ATTACKER, "result": "success"})
events.append({"ts": t_export.isoformat(), "event": "export.completed", "user": "svc-backup", "src_ip": ATTACKER, "bytes": 5242880, "trace_id": "trace-lab-001"})
for i in range(5):
    events.append({"ts": (t_success - timedelta(minutes=2 + i)).isoformat(), "event": "auth.login", "user": "svc-backup", "src_ip": ATTACKER, "result": "failure"})

(OUT / "auth.log").write_text("\n".join(auth) + "\n", encoding="utf-8")
(OUT / "nginx-access.log").write_text("\n".join(access) + "\n", encoding="utf-8")
(OUT / "app.json").write_text("\n".join(json.dumps(e) for e in events) + "\n", encoding="utf-8")
print(f"auth={len(auth)} access={len(access)} app={len(events)}")
```

```bash
cd ~/siem
python3 make_logs.py
head -n 3 logs/auth.log
tail -n 3 logs/nginx-access.log
cat logs/app.json
```

### Index the data

Register each file with the right sourcetype so Splunk parses timestamps and fields:

```bash
docker exec splunk /opt/splunk/bin/splunk add monitor /logs/auth.log \
  -index main -sourcetype linux_secure -auth "admin:$SPLUNK_PASSWORD"
docker exec splunk /opt/splunk/bin/splunk add monitor /logs/nginx-access.log \
  -index main -sourcetype access_combined -auth "admin:$SPLUNK_PASSWORD"
docker exec splunk /opt/splunk/bin/splunk add monitor /logs/app.json \
  -index main -sourcetype _json -auth "admin:$SPLUNK_PASSWORD"
```

In the search app, set the time range to **All time** and confirm the counts:

```spl
index=main | stats count by sourcetype
```

Checkpoint: three sourcetypes, with 70 authentication events, 106 access events, and 7 JSON events. If a count is zero, the monitor path or sourcetype is wrong; see the troubleshooting section.

## Step-by-step tasks

1. **Read the raw evidence before trusting the SIEM.** Open the three files and identify the attacker address, the targeted accounts, the successful login time, and the large export. Write a one-paragraph "what I think happened" hypothesis in your notes. Checkpoint: your hypothesis names a start time, an account, and one data source you will use to confirm it.

2. **Build the brute-force detection.** Extract the source IP, bucket events into five-minute windows, and flag windows with eight or more failures.

```spl
index=main sourcetype=linux_secure "Failed password"
| rex "Failed password for (?:invalid user )?(?<target_user>\S+) from (?<src_ip>\d+\.\d+\.\d+\.\d+)"
| bin _time span=5m
| stats count values(target_user) as targeted_accounts by _time, src_ip
| where count >= 8
| sort - _time
```

Checkpoint: the query returns windows for `203.0.113.45` with counts well above eight, and no normal source appears. Save it as a report named `LAB - SSH brute force threshold`.

3. **Find the success that follows the failures.** This is the query that turns noise into an incident. Count failures and successes per source, then filter for sources with many failures and at least one success.

```spl
index=main sourcetype=linux_secure ("Failed password" OR "Accepted password")
| rex "(?<action>Failed|Accepted) password for (?:invalid user )?(?<target_user>\S+) from (?<src_ip>\d+\.\d+\.\d+\.\d+)"
| stats count(eval(action="Failed")) as failures
        sum(eval(action="Accepted")) as successes
        values(target_user) as users
        by src_ip
| where failures > 20 AND successes > 0
```

Checkpoint: exactly one row, `203.0.113.45`, with more than twenty failures and one success. Record the successful account.

4. **Examine privileged activity after the login.** Look for `sudo` commands and reconstruct what the account did.

```spl
index=main sourcetype=linux_secure "sudo:"
| rex "sudo:\s+(?<actor>\S+)\s+:.*USER=(?<run_as>\S+)\s+;.*COMMAND=(?<command>.+)$"
| table _time, actor, run_as, command
| sort _time
```

Checkpoint: a `tar` command creating `/tmp/backup.tgz` from `/var/backups`, attributed to `svc-backup` running as root. Explain why archiving backups is a collection step rather than normal administration in this context.

5. **Correlate the web tier.** Pivot on the attacker address and look for reconnaissance and the export in the access log.

```spl
index=main sourcetype=access_combined "203.0.113.45"
| stats count, min(_time) as first_seen, max(_time) as last_seen,
        sum(eval(status="401")) as unauthorized,
        max(bytes) as largest_response
        by clientip, uri
| sort - largest_response
```

Checkpoint: repeated `/admin` requests returning 401, then a single `/api/v1/export` returning 200 with a 5,242,880-byte response.

6. **Correlate the application tier.** Parse the JSON events and confirm the application recorded the same actor and export.

```spl
index=main sourcetype=_json
| spath
| search event=export.completed
| table _time, event, user, src_ip, bytes, trace_id
```

If `spath` returns nothing, the events were indexed as plain text; use `| fromjson _raw` instead. Checkpoint: one export event with the same user, source IP, and byte count as the web log.

7. **Build a single timeline.** Put the three sources on one axis and keep only the fields an investigator needs.

```spl
index=main (sourcetype=linux_secure OR sourcetype=access_combined OR sourcetype=_json)
| eval actor=coalesce(src_ip, clientip, user)
| eval detail=coalesce(command, uri, event)
| table _time, sourcetype, actor, detail, status, bytes
| sort _time
```

Export the result as CSV, then reduce it to the twelve to twenty events that actually change the story. Checkpoint: a timeline that a reader can follow without opening the SIEM, with timestamps in UTC and the source named on every row.

8. **Write the triage note.** Use this structure: summary, severity and rationale, confidence, evidence with links to saved searches, scope, false-positive analysis, recommended actions, detection gaps. Severity for a successful external login followed by a large export is at least High; justify it rather than asserting it.

9. **Test the benign explanation.** Suppose `svc-backup` routinely logs in from a backup provider's address. What evidence would support that? Check whether the address appears before the brute force, whether the login used a key or a password, whether the account normally runs `tar`, and whether the export matches a scheduled job. Write down which facts rule the benign explanation in or out. Checkpoint: at least two facts that discriminate between the two hypotheses.

10. **Recommend containment and recovery for the lab.** In a real incident you would disable the account, revoke sessions and keys, block the source, preserve evidence, and check for additional persistence. In this lab, write the actions and the order you would take them, plus the evidence you would collect first. Do not actually block addresses or delete logs; the value is in the plan.

11. **Improve the detections.** Add two detections that would catch variants your first query misses: a low-and-slow spray (five failures per hour across many accounts) and an unusual data-volume threshold for the export endpoint. Write each as a saved search with a name, a schedule recommendation, and a false-positive note.

12. **Build a small dashboard.** Create panels for failed logins over time by source, top targeted accounts, unauthorized web requests by URI, and largest responses by client. Keep it to four panels; a dashboard nobody reads is decoration.

13. **Document the SIEM limitations.** Splunk Free has no scheduled alerting and no authentication, so your "alerting" is a saved search plus a manual or external schedule. Write how you would implement the same detections in Wazuh or Elastic if you needed real-time alerts, and what would change in the workflow.

## Troubleshooting

### Splunk never becomes healthy

Check `docker logs splunk` for license acceptance and password errors. The container requires `SPLUNK_START_ARGS=--accept-license`, a password that meets the complexity rules, and roughly 4 GB of RAM. If port 8000 is already in use, map a different host port but keep the `127.0.0.1` bind. Give the container two to three minutes on first start before concluding it failed.

### Searches return no events

Three things cause this in order of likelihood: the time range is not **All time**, the monitor path is wrong inside the container, or the sourcetype did not parse. Verify the file is visible with `docker exec splunk ls -l /logs`, check `index=main | metadata type=sourcetypes`, and confirm the inputs with `docker exec splunk /opt/splunk/bin/splunk list monitor -auth "admin:$SPLUNK_PASSWORD"`. Remember that the synthetic events are dated 2026-10-31; a default "Last 24 hours" window may exclude them later.

### `rex` extracts nothing

Test the expression against one raw event with `| makeresults | eval _raw="..." | rex "..."` before blaming the search. Watch for the difference between `Failed password for invalid user` and `Failed password for` (the non-capturing group `(?:invalid user )?` handles both), and escape backslashes correctly inside SPL strings. Use `| rex field=_raw` when the field is not `_raw`.

### JSON events are not parsed

The `_json` sourcetype performs automatic extraction, but only if the events were indexed as JSON rather than as a single multiline blob. Confirm with `index=main sourcetype=_json | head 1` and check the raw text. If needed, add `| fromjson _raw` or define `KV_MODE=json` for the sourcetype in `props.conf`. Do not "fix" this by reindexing repeatedly; fix the input once.

### The license limit is reached or Splunk stops indexing

Splunk Free indexes up to 500 MB per day. The synthetic dataset is a few kilobytes, so a limit error usually means something else is being monitored, such as a whole `/var/log` directory. Remove the extra monitor, delete the test index data if you were experimenting, and restart the container. Check `Settings > Licensing` for the actual volume before changing anything.
